# How to Query This Repo

Two ways to search the research/design-tokens archive: ask an agent in natural language, or
open the visual search interface. Both read the same underlying files — neither is more
"authoritative" than the other.

## Option 1 — Ask Claude Code (or any agent that reads AGENTS.md)

Open a Claude Code session in this repo (IntelliJ or terminal) and just ask, in plain English.
`AGENTS.md` already tells it how the repo is organized and to search `findings/` first, falling
back to `raw/` only to verify or quote. You don't need to reference file paths or frontmatter
syntax — describe what you want to know.

**Good query patterns:**

- *"Have we tested anything about [topic]?"*
  → e.g. "Have we tested anything about alert fatigue?" — it should find
  `clinician-experience-documentation-burden.md` and `care-coordination-triage.md`, both of which
  discuss the same alert-fatigue pattern independently, and cite the raw sessions behind each.

- *"What did we learn from the [method] we ran on [date/topic]?"*
  → e.g. "What did we learn from the ambient scribe usability test in September?" — pulls the
  specific raw session, not just the synthesized finding.

- *"Has [X] shown up more than once?"*
  → e.g. "Has the color-only status accessibility bug shown up in more than one audit?" — this is
  exactly the kind of cross-cutting pattern `findings/accessibility-cross-cutting.md` and the
  December executive retro both call out; a good query should surface both.

- *"What's still an open question about [topic]?"*
  → pulls the "Follow-ups / Open Questions" section from relevant raw sessions.

- *"What haven't we scoped in yet, and why?"*
  → e.g. surfaces `scope-boundaries-and-workflow-fit.md`'s deliberate exclusions (behavioral
  health, ED intake during peak hours) — useful for "did we already decide not to do X."

**If the answer feels incomplete:** ask it to check `research/_index.md` directly, or to grep
`research/findings/tags.md` for a specific tag. The retrieval strategy is explicitly
keyword/tag-based, not semantic — an unusual phrasing might miss something a more literal
rephrase would catch.

## Option 2 — Open research/search.html

No agent, no server, no build step at query time — just open the file in a browser.

- **Search box** — matches against title, tags, and full body text (substring match, not fuzzy).
- **Kind filter** (sidebar) — Sessions / Findings / Components / Analytics / Deliverables. The
  last bucket covers all 20 feature-002 folders (personas, wireframes, research-plans, ...).
- **Type filter** — usability-test, interview, survey, etc. for Sessions/Findings; for
  Deliverables, the specific folder (Persona, Wireframe, Research plan, ...).
- **Tag filter** — click chips to narrow; multiple active tags are AND'd together, not OR'd.
- Click any result row to expand its full content inline, including a link to the underlying
  source file.

This is generated by `research/scripts/build_search_ui.py` from the same frontmatter and content
an agent would read — **re-run it after adding new raw sessions or findings**, since it's a
snapshot, not a live view. It won't update itself.

```bash
python research/scripts/build_search_ui.py
```

## Which one should I use?

- Ask a specific question, want a synthesized answer with reasoning → **Claude Code**
- Browsing/skimming, filtering by tag or type, don't have a specific question yet →
  **search.html**
- Something feels stale or missing from either → check `research/_index.md` was regenerated
  recently (`python research/scripts/build_index.py --check`)
